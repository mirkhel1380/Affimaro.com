# Platform subscription checkout

The owner connects Affimaro subscriptions from `/owner/settings#stripe-connection`. This owner-only form accepts a live restricted Stripe key for the selected existing account. It verifies the account, live charges and all six role-specific fixed USD monthly prices, then creates a dedicated customer portal configuration and a signed subscription webhook. It does not create a customer, Checkout Session or charge.

Brand plans are Starter $19, Growth $49 and Business $99 USD per month. Agency plans are Starter $39, Growth $79 and Business $149 USD per month. Brand provider identifiers and fixed agency lookup keys are in `lib/platform-billing-catalog.ts`. New agency purchases require the separate agency catalog entries. Existing agency subscriptions and saved unresolved payments retain their recorded verified prices. Creator and affiliate access remains free.

Required restricted-key resources are shown in the private form: Accounts and Balance read; Products and Prices read; Checkout Sessions and Customers write; Customer Portal write; Subscriptions and Invoices read; Webhook Endpoints write. Transfer, payout and bank permissions are separate from this software subscription connection. The ChatGPT Stripe app's OAuth connection does not supply a server runtime key.

The additive `0013` migration introduces encrypted platform configuration, minimal webhook delivery records and versioned Checkout payload fields. Platform keys and webhook signing secrets use the existing `PAYMENT_DATA_KEY_V1` with separate authenticated contexts. Original authentication/payment keys, identities, workspaces and financial records are preserved. Settings, credentials and signing secrets are never returned to customer pages or public downloads.

Both setup POST payloads and idempotency keys are frozen before submission. Unknown setup responses retry the same operations within 23 hours; older or changed-account/domain setups require operator reconciliation. Invalid replacements never overwrite the existing credential. Explicit key rotation and domain changes must reconcile the existing setup rather than registering an untracked duplicate. The dedicated customer portal supports invoices, payment method updates and cancellation at period end. Profile approval is required once. Package selection and verified subscription payments need no second owner review; an existing subscription must be managed before a different purchase can be opened.

Public package selection explains registration, review and payment as three steps. Approved brands and agencies with a verified session go directly to their own billing page. Pending accounts stay in application review. A selected package displays its provider-verified amount and recurring-payment confirmation before opening Checkout. An unresolved saved payment must be reconciled before selecting a different package. GET requests do not create Checkouts or charge cards.

New Checkouts use dynamic payment methods and a durable integration identifier with eight random letters. Version 1 unknown Checkout POSTs remain held; they are not replayed with a changed payload. Known older Sessions can still be checked. Creating or returning from Checkout never substitutes for authoritative paid-provider evidence.

`POST /api/billing/webhook` alone bypasses browser-session authentication. It requires a valid raw-body Stripe signature within five minutes and the configured account/mode. It handles Checkout completion/async outcomes, subscription lifecycle events and paid/failed invoices. Notifications resolve existing workspace/attempt identifiers, re-read Stripe and use the same validated billing reconciliation path. Unpaid async completion cannot activate access. Replays are deduplicated, concurrent work is leased, and transient failures remain retryable. No event payload, bank details or provider secrets are stored in the delivery ledger.

Subscription enforcement is required by default, and saved platform setup always enforces it. Before a runtime key is connected, checkout remains explicitly unavailable. A connected provider, verified price or registered webhook is not proof of a real customer payment. Customer email delivery also still requires a verified sender; the public and owner domains remain separate and the existing signed subscription callback is preserved.

The old migration-v1 transfer format remains frozen. Its tests use the historical source schema, verify import into the additive current target, and assert that the exporter refuses the newer billing schema rather than omitting new subscription configuration. Do not repeat the already completed migration/import.

Validation includes isolated Stripe responses, real SQL migrations, real server-page rendering, raw-body signature failures, unpaid async events, duplicate/out-of-order events, cross-workspace correlation, lost creation responses, atomic database rollback and the actual initial payment review. No real customer, Checkout Session or charge was created by implementation tests. Live credential activation and a real merchant/customer walkthrough remain owner actions after deployment.

## Payment confirmation and return recovery

An embedded Checkout completion and the saved Checkout return URL both open the same confirmation flow. The authenticated `confirm` billing action reconciles the current saved payment and returns only a status and environment; it never exposes a Checkout client secret, provider customer or subscription identifier. It uses the saved payment's package context, not a submitted package or URL assertion.

The customer sees separate states for a verified active subscription, processing payment, unfinished form, expired Checkout, subscription requiring attention and a completed test purchase. A return query parameter alone never activates access. Payment and a paid invoice must still pass the existing provider checks, and signed webhooks continue to fulfill and reconcile subscriptions independently of the browser.

A completed Checkout with an unpaid delayed payment remains attached to its original saved attempt. Checking, resuming or trying to cancel that processing attempt does not start or expire a second payment. A provider-verified delayed failure is linked to its existing subscription without granting access, so invoice retries and later signed invoice success can recover it without a second purchase. Expiring an open unpaid form still requires explicit confirmation. Unknown provider results and proof mismatches retain their existing reconciliation protections.

Automatic confirmation makes at most six sequential checks with short increasing waits, then offers manual rechecking. Leaving the component stops further checks and ignores late results. Network failures show a retry and a route back to billing. Confirmed live payments reload the role's canonical billing page before continuing to the brand or agency portal. Test purchases do not activate live access; affiliate and creator accounts remain free.

Validation uses isolated databases and provider fixtures. It does not charge a real card, create a live Checkout Session, change Stripe setup or prove customer email delivery or production embedded-form activation.

Login return paths preserve the validated package and Checkout-return or cancellation flags for both business portals. If authentication is needed after payment, signing in resumes saved-payment confirmation instead of losing the return context.
